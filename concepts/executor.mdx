---
title: "Executor"
description: "The per-resource failure-state machine that owns everything that happens once a proposal ships."
---

The executor is what `ubx ship <proposal-id>` actually runs. It owns
failure semantics end to end — nothing about how a real cloud apply can
partially fail, hang, or return an ambiguous result is left to the
provider layer or bolted on afterward. This is the reliability
differentiator the [Architecture](/architecture) page's trust chain
depends on: what applies is exactly what was signed, and the executor is
what makes that true even when the network isn't cooperating.

## Per-resource state machine

```
pending ──► in_flight ──► applied
                       ├─► failed
                       └─► unknown_post_timeout
                                 │
                                 ▼
                     reconcile-by-query (ReadResource)
                                 │
                 ┌───────────────┼───────────────┐
                 ▼               ▼               ▼
              applied         failed        still_unknown
```

`unknown_post_timeout` exists because a provider can fail *after* it has
already changed something — the executor never assumes success or failure
from how a call ended. It reconciles by querying the provider directly
for the resource's real current state before deciding anything.

A timeout is the obvious way to get there, and not the only one. A
provider that creates a resource and *then* fails, returning a structured
error about its own response handling, has changed the world just as
surely as one that never answered. Both land here.

## Idempotency, by contract

`ubx ship` is safe to re-run any number of times. Each resource's
behavior on re-run depends on its last sealed state: `applied` is
skipped outright, `failed` retries from `pending` within a bounded retry
budget, `still_unknown` reconciles again before any new apply call is
made — never a blind re-apply on top of something still unresolved. A
proposal whose every resource already landed reports a genuine no-op and
writes nothing new.

## Error taxonomy: retryable vs. terminal vs. stale

- **Retryable** — a transient signal that doesn't rule out the change
  having landed (a deadline exceeded before a response, a transport
  reset). Feeds reconciliation and the retry budget.
- **Terminal** — a real, structured error from the provider itself. The
  call is not repeated within this `ship` invocation: a provider that
  already said an attribute is invalid won't answer differently on an
  immediate retry with the same input.

  It does **not** mean the change did not happen. A diagnostic answers
  "did the operation complete", not "does the resource exist", and those
  come apart exactly when it matters most, when a provider has already
  changed something and then fails. So a terminal error reconciles like
  any other unresolved result. Reconciliation only ever reads, so this
  costs a query, never a second apply.
- **Stale** — a freshness check failed: reality moved since this proposal
  was resolved. See [Staleness](/concepts/staleness) — this is a
  distinct classification from both of the above, because nothing was
  rejected, the ground just shifted.

## A create is the one thing that cannot verify itself

Reconciliation works by reading the resource back, which needs a lookup
key: the attributes that identify one instance to the provider. A modify
or a destroy already has one, recorded when the resource was first
created or adopted. A create does not. It is being created, so nothing
identifies it yet, and the key is derived from the *result* of the very
call that just failed.

So a create whose outcome is unknown stays unknown. The executor cannot
settle it, and does not pretend to: the resource is recorded as
unverified, its dependents stay blocked, and a human resolves it.

That makes the message the entire mechanism. Every other unresolved
result is followed by read-back attempts that narrate what is happening,
so the receipt tells the story on its own. A create has nothing to
narrate, and an error message alone reads as "it did not happen", which
is exactly the wrong conclusion. An unverified create therefore prints
its own line saying what is actually true: the call was made, the
resource may exist, nothing is recorded for it, a re-run would create
another, and here is the `ubx scan` command that adopts it if it is
there.

A silent orphan is the failure this design exists to prevent, and a
correct record nobody reads would only have made it quieter.

## Scope grows deliberately, not implicitly

The executor's first version shipped only `drift_revert` proposals — the
one kind where every value being written back is already fully
concrete, letting it skip a distinct plan phase and go straight to
apply. Shipping resolver-produced `change` proposals, where a value can
still be `$computed` at ship time, was a later, explicit amendment, not
an assumption the first version already covered it.
