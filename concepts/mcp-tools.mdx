---
title: "MCP Tools"
description: "Independent tools, not a pipeline -- and the two lines drawn around what an assistant is allowed to do on its own."
---

`ubx mcp` (UBI-25) serves the Model Context Protocol over stdio, in the
same binary, as a cobra subcommand -- there is no second `cmd/ubx-mcp`
executable, and no parallel API. Every tool it exposes is a thin
wrapper over primitives the CLI's own `--json` code paths already call,
returning the exact same struct types the CLI already produces. Eight
tools exist today, in two groups added a session apart: three read-only
ledger tools (UBI-25), and five blueprint-authoring tools (UBI-223).
Both groups share one governing idea, stated once here so it doesn't
have to be re-derived per tool: **an irreversible or externally-visible
act stays a human's own decision, and a tool that could make one is
simply never registered, not gated by a runtime check.**

## The three ledger tools (UBI-25)

`ubx_why`, `ubx_status`, `ubx_scan` -- each wraps the identical
`compute*JSON` function (`cli/mcp_why.go`/`cli/mcp_status.go`/
`cli/mcp_scan.go`) the CLI's own `--json` flag already calls. `ubx_scan`
is the one tool in this group capable of a real network read against
live infrastructure; it never becomes a write, there is no accept path
attached to it. `ubx accept`, `ubx ship`, `ubx writeback`, `ubx
revert-plan`, and `scan --surface-as` (which opens a real GitHub
issue/PR) are the omissions this group is defined by -- named explicitly
in both `--help` and the docs page, not left to be inferred from a
missing tool.

## The five blueprint-authoring tools (UBI-223)

`draft_ubxfile`, `validate_ubxfile`, `build_blueprint`,
`list_blueprints`, `describe_blueprint`, all in `cli/mcp_blueprint.go`.
The ticket that proposed this group named six tools, including
`push_blueprint`, and left two questions open. Both were answered
before anything was built.

### Why `push_blueprint` isn't the sixth tool

`ubx blueprint push` (`blueprint/oci.go`) is a real ORAS upload to a
real OCI registry -- the one irreversible step in a blueprint's
lifecycle, and the one step every other consumer (`blueprint.Pull`)
treats as trustworthy once it happens. This is the identical shape the
ledger group's own omissions already established: an assistant can help
shape a blueprint, but publishing it is a human act, done by running the
real CLI command on purpose. `push_blueprint` is not gated behind a
flag or a confirmation prompt -- it is simply never registered, the same
omission-not-gate discipline the ledger group set first.

### Why every tool returns content instead of writing it

`draft_ubxfile` assembles an `Ubxfile` and a `resources.json` from
agent-supplied pieces and returns both as strings. There is no repo for
an assistant to have opened, and keeping it that way means committing
the result stays a human act -- the same "never accepted" posture
`ubx_scan` already has for a live read. `build_blueprint` carries one
explicit, additive exception: an `out_dir` input, mirroring `ubx_scan`'s
own `out` field. When given, the generated go/ts/py files are also
written there, on top of the inline response, never instead of it.
Nothing else in the group touches a caller-supplied path.
`validate_ubxfile`'s and `build_blueprint`'s own `dir` input is
read-only, and the one place any tool in this group writes to disk at
all, for inline content with no `dir` given, is a throwaway
`os.MkdirTemp` scratch directory, one per call.

### One validation implementation, not two

`decodeBlueprint` (`blueprint/decode.go`) already existed before this
work, as the single language-neutral check `GenerateGo`/`GenerateTS`/
`GeneratePython` each ran internally before their own codegen -- every
resource is `op:create`, no duplicate addresses, every `for_each` names
a real declared list-typed param, every `$ref`/`depends_on` resolves
against a sibling resource, topological ordering succeeds, every
`outputs:` target resolves to a real resource attribute. UBI-223 added
exactly one new entry point in front of it:

```go
func Validate(dir string) (*Ubxfile, *resolver.IntentFile, error) {
	ubxfile, err := ParseUbxfile(dir)
	if err != nil {
		return nil, nil, err
	}
	var draft resolver.IntentFile
	if err := json.Unmarshal([]byte(ubxfile.Resources), &draft); err != nil {
		return nil, nil, fmt.Errorf("blueprint: resources: is not a valid pre-resolved intent/v1 document (%s): %w", ubxfile.ResourcesSource, err)
	}
	if _, err := decodeBlueprint(&draft, ubxfile.Params, ubxfile.Outputs); err != nil {
		return nil, nil, err
	}
	return ubxfile, &draft, nil
}
```

`ubx blueprint build`'s own CLI `RunE`, `validate_ubxfile`, and
`build_blueprint` all call this same function -- none of the three
carries a parallel copy of the check. This was a deliberate constraint
on the build, not an incidental convenience: two independent
implementations of the same fold silently diverging is the exact shape
that produced UBI-197 and UBI-233, and the fix here is structural, one
function with three callers, rather than a rule to remember on the next
change.

### Why `draft_ubxfile` invokes no second LLM

The ticket that proposed this tool predates UBI-224, which removed
blueprint build's own intent-provider draft step entirely.
`resources:` is now always a pre-resolved `ubx:intent/v1` document, the
same wire shape `ubx resolve --from-code --out <file>` produces, never
prose for a model to interpret -- `blueprint.Ubxfile.Resources`'s own
doc comment states this directly: build "has nothing left to interpret,
only to parse." `draft_ubxfile` reflects that structurally: it is
deterministic assembly of agent-decided pieces (a resources array the
calling assistant has already reasoned about, plus params/outputs
specs) into the two files a blueprint directory needs, self-validated
via the same `blueprint.Validate` every other tool in this group calls,
before ever being handed back. There is no drafting intelligence inside
the tool itself to keep in sync with anything as the intent-provider
pipeline evolves, because there no longer is an intent-provider
pipeline to keep in sync with -- the assistant supplies the reasoning,
the tool supplies the exact wire shape and the validation.

### Why `list_blueprints` walks a filesystem instead of querying a registry

Strata's own registry service isn't built yet -- `blueprint.Pull`'s own
four real source forms (local directory, bare tarball, git URL+ref+path,
`oci://` ref) are all still "a caller already has a ref in hand," never
a discovery mechanism. Aggregating ledger-wide `BlueprintName`
provenance (`ResourceBinding.BlueprintName`, `sdk/go/runtime/runtime.go`)
was considered and set aside -- it would require new cross-resource
aggregation logic no existing function exposes today, a real, separately
scopable piece of work, not a small addition. `list_blueprints` instead
walks a given root directory (skipping `node_modules`/`.git`) for real
`Ubxfile`-rooted directories and validates each one it finds,
best-effort -- an invalid blueprint is reported with its own error,
never fails the whole call. The tool's own description says plainly
that this reports what's on disk today, not a registry query, so a
caller doesn't read more into the result than the implementation
actually provides.

`describe_blueprint` pulls one of the four real source forms into a
scratch directory via `blueprint.Pull`, attempts `blueprint.Verify`
(tamper-evidence hash check, succeeds only for an already-packaged
blueprint) and `blueprint.Validate` independently -- both attempted
regardless of the other's outcome, since a pulled source can be
packaged without being a valid Ubxfile-rooted blueprint, or vice versa
-- and reports whichever succeeded. The scratch directory is always
removed after; nothing about this tool is a write.

## The drive-by fix this work required

`ubx blueprint convert`'s own doc comment (`cli/blueprint_convert.go`)
described re-running `build` against a converted directory as "not
guaranteed to reproduce" -- true before UBI-224, wrong after it. A
converted blueprint's own `resources:` field is documentation-only
summary text (`res.Summary`, a string), never valid `intent/v1` JSON,
and `blueprint.Validate`'s new unmarshal step means running `build`
against one now fails outright with a JSON parse error, not merely a
best-effort mismatch. The comment was corrected to state the real
current behavior directly, not softened to "no longer applicable" --
the next reader needs to know it fails hard, not just that the old
guarantee is gone.
