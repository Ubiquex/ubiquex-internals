---
title: "Blueprints"
description: "Signed, reusable, parameterized proposal templates -- compiled once, called from the SDK, zero AI anywhere in the lifecycle."
---

A blueprint is a reusable, parameterized template for a piece of
infrastructure -- authored once, compiled into real SDK code, and
called from the SDK. The point is repeatability with provenance:
calling a blueprint twice produces two independently traceable
results, not a copy-pasted config nobody remembers the origin of.

## Author, build, call, distribute, verify

The real lifecycle, each stage backed by working code, not a design
sketch:

1. **Author** -- a blueprint is written as an Ubxfile: language, params,
   and `resources:`, a pre-resolved intent/v1 document (the same shape
   `ubx resolve --from-code --out <file>` produces) that the author
   produces themselves, via the SDK or `ubx blueprint convert`. This
   stage and the next are being replaced: see
   [Blueprints become code](#blueprints-become-code-and-the-schema-is-derived).
2. **Build** -- `ubx blueprint build` parses that pre-resolved document
   once (it does not interpret or draft it -- nothing in this step
   calls an LLM) into real, compilable SDK packages (Go, TypeScript,
   Python).
3. **Call** -- a hand-written SDK program, either a direct import of the
   compiled function or a `blueprint_calls` wire entry, expanded by
   directly invoking the target blueprint's own compiled function --
   zero AI involved in the expansion itself.
4. **Distribute** -- a local path, a git repo and ref, a real OCI registry
   (`ubx blueprint push`/`pull oci://...`), or an offline tarball.
5. **Verify** -- `ubx blueprint verify`, one content-hash scheme
   regardless of which distribution mechanism a blueprint arrived
   through.

## Blueprints become code, and the schema is derived

The Author and Build stages above describe the Ubxfile model, which is
being replaced. A blueprint is becoming ordinary code in one language:
no Ubxfile, no `resources:` document, no generated bindings. An author
writes a function, and it imports the published SDK like any other
program would.

That removes the thing the Ubxfile was actually for. A caller still has
to know a blueprint's parameters, their types, which are required, and
what it returns, and with the Ubxfile gone there is nothing declaring
them. The answer is that nobody declares them: **the schema is derived
from the function's own signature at package time** and written beside
the code as `blueprint.schema.json`, covered by the same content hash as
every other file in the package.

Derivation rather than declaration is the whole point. A written
document can disagree with the function it describes; a derived one
cannot. A consumer never re-derives it, it reads what the package ships.

### One sentence, three spellings

The authoring convention is a single rule, expressed in whatever the
language already has:

| Language | Required | Optional |
| --- | --- | --- |
| Go | a non-pointer field | a pointer field, omitted when nil |
| TypeScript | a property with no `?` | a property with `?` |
| Python | a bare annotation | `Optional[X] = None` |

Each extractor reads declarations only, and none of them runs the
blueprint. Go is parsed with `go/parser` from the standard library.
TypeScript is read with `deno doc --json`, Deno's own documentation
generator. Python is parsed with CPython's own `ast` module on the
pinned WASI interpreter. The last two are not new dependencies: they are
the binaries those evaluators already require, so a blueprint that can
be evaluated can be extracted.

Using each language's real parser is a deliberate trade against
hand-rolling three. TypeScript's type syntax is large and Python's
grammar is significant-whitespace with annotations that may be strings,
so a hand-written reader of either is wrong in exactly the cases a real
blueprint hits, and wrong silently: the failure mode is a schema that
quietly disagrees with its own function, which every consumer
downstream then shares.

### Where the three cannot agree

Three asymmetries are real, and are recorded rather than smoothed over,
because each one changes what an author can write:

- **Python cannot interleave required and optional params.** A dataclass
  field with no default may not follow one with a default, so required
  params must come first. Go and TypeScript may interleave freely, so a
  Go blueprint can have a parameter order no Python blueprint can
  reproduce. The Python extractor refuses the interleaved case at
  extraction, where the message can name the constraint, rather than
  leaving it to a `TypeError` the first time anything imports the
  module.
- **TypeScript needs its dependencies installed.** `deno doc` resolves
  the whole module graph and emits nothing if any import is
  unresolvable, including imports the signature never mentions. Go reads
  an undownloaded tree, and Python's `ast.parse` resolves no imports at
  all.
- **TypeScript can verify where a type came from.** Deno tags each type
  reference with its resolution, so a `CrossMarker` imported from
  `@ubx/sdk` is distinguishable from a local type sharing the name. Go
  matches on source spelling to avoid type-checking and cannot. This is
  a difference in strictness, not vocabulary: all three accept the same
  set of well-formed blueprints.

### What the schema deliberately does not carry

**Default values.** Under the Ubxfile a default was declared and
`describe_blueprint` reported it. Under the config-struct convention an
optional parameter's default lives in the function body, where no
extractor can see it without executing code. That is a real regression,
accepted rather than paid for with a `Defaults()` convention an
extractor would have to parse, which is the parse-a-convention
requirement the config struct was chosen to avoid. The schema says so
explicitly in a `defaults` block carrying `derivable: false` and the
reason, so a reader can tell a deliberate absence from a failed
extraction, and so `describe_blueprint` can report "optional, default
not derivable" rather than an ambiguous "optional".

**Anything a language cannot state.** Where an extractor asserts
something the source could not express, it records the assertion. There
is exactly one today, and only in TypeScript: this vocabulary's `number`
means integer and TypeScript's `number` admits fractions, so a
TypeScript-derived schema carries that assumption in a `derivation`
block. Go and Python state `int` outright and carry nothing.

### What reads it

`ubx blueprint package` is where a schema is derived and written, and
every consumer that used to open the Ubxfile now reads whichever
document a blueprint actually carries. One function decides that, so
the precedence cannot be decided differently in six places: **the
schema wins where both exist**, because it is derived from the function
and the Ubxfile is written by hand, so when they disagree the derived
one is the one that cannot be stale.

The schema is written *before* the manifest, so the content hash covers
it like every other file; one outside the hash could be swapped after
packaging. It is re-derived on every package rather than reused, since
a schema that could be stale defeats the reason for deriving it.

Calling a blueprint that is code needed new caller writers rather than
adapted ones. There are no `go/`, `ts/`, `py/` subdirectories; the
blueprint's own root is the package; and the function and config type
are the real ones the schema recorded, where the Ubxfile model derived
both from the blueprint's *name* and an author had no say in either.
Go's positional arguments with trailing functional options become a
config literal with named fields, which removes an entire class of
argument-ordering bug, and an un-given optional is omitted from the
literal entirely in all three languages rather than passed as null.

`source_name` is what makes that possible at all: a config literal
names fields by their real identifiers, and no case conversion of
`target_arn` produces `TargetARN`.

An author can see all of this without packaging: `ubx blueprint
describe` derives the schema and prints it, including each param's own
source identifier. It derives rather than reading back a written
`blueprint.schema.json`, because the question being asked is what the
blueprint will become, and reading the file would answer what it became
last time.

### How outputs resolve, and why the runtime had to change

The two models resolve outputs differently, and have to, because they
know different things.

An Ubxfile declared each output as a `"<resource-slug>.<attribute>"`
target, readable without running anything, which is exactly the pair
needed to build a real address. A blueprint that is code returns a
`Computed`, and which attribute of which resource that points at can
depend on the blueprint's own branching. Nothing outside the evaluation
can derive it, and reading it from source would mean interpreting the
function body, which is the thing the derived schema exists to avoid.

So the evaluation reports it. The synthesized caller passes each
returned output to the runtime's own `BlueprintOutputs`, and the
evaluated intent document comes back carrying `blueprint_outputs`,
output name to resolved address. That is one new optional field on the
intent document, additive, omitted rather than empty for every document
a person writes, and it is ordinary hashed content.

This is the clearest case in the system of a question that **cannot** be
answered by reading, only by running. The schema mechanism answers
everything else about a blueprint without execution: names, types,
required-ness, the entrypoint. It cannot answer this one, and adding
more of it would not have helped.

Two consequences:

- A declared output the blueprint never sets is refused by name at the
  call, which is a better place to fail than at whatever config
  happened to reference it.
- The caller only reports outputs when the blueprint declares any, so a
  blueprint without them still compiles against an older SDK.

## Every call is provenance-tagged

A resource a blueprint call produced carries `{"kind": "blueprint", "ref":
"<name>:<content_hash>"}` in its own provenance, and `ubx why` renders
that chain honestly — a blueprint-produced resource never looks
indistinguishable from a hand-authored one.

How a resource learns which blueprint produced it depends on which model
the blueprint used. A built blueprint's generated code says so directly;
a blueprint written as code says nothing about itself at all, by design,
so it is attributed by where the call came from instead. See
[Call-Site Attribution](/concepts/call-site-attribution). `ubx render` groups a
blueprint's own output visually too, so a diagram stays legible even
when most of its nodes came from one call.

## The declaration says where, the lock says what

A resolved proposal has always recorded which blueprint content produced
a resource. Nothing recorded which content a stack was *supposed* to
use. That asymmetry is easy to miss because the ledger looks complete:
ubx recorded the answer and had no way to state the question.

The consequences were not subtle once you look for them. A fresh clone
could not reconstruct the blueprint, because the pulled directory was
untracked working state with no convention about whether it belonged in
version control. Two people could resolve the same stack from the same
declaration against different content, both successfully, with nothing
comparing them. And a blueprint's own manifest records its content hash
and no origin at all, so a pulled directory cannot say which reference
produced it.

So a stack now declares its blueprints in config, and a committed lock
file records what each declaration resolved to, source and hash
together. The source is recorded as well as the hash precisely because
the blueprint's own manifest cannot: the link between a reference and
the content it produced exists nowhere else.

Planning writes the lock. Resolving checks it and refuses on
disagreement, and deliberately writes nothing, because resolve prints a
draft and is reached by scripts that do not expect their working tree to
change. Getting past a refusal is always explicit.

Two disagreements are reported differently, and the difference is the
point. A changed declaration means the lock is simply behind, which is
ordinary. Content moving under a declaration nobody changed means either
a mutable tag was repointed or a registry is serving different bytes
than before, and the right first move is to find out which, not to
accept it. Suggesting the update flag first in that case would be
answering a question nobody asked.

The mechanism is opt-in by construction: no lock file means a stack has
not adopted it, and enforcement begins when the file exists. That is not
politeness, it is the difference between adding a feature and breaking
every stack that already worked.

### The lock and the ledger call a blueprint different things

Worth knowing before comparing one against the other, because the obvious
comparison is wrong and quietly so.

A lock entry is keyed by the name the **call** used, derived from the
source's last path segment with any version stripped. A ledger reference
carries the blueprint's own **packaged** name, from its build-time
record. An OCI repository called `rev-bp` can hold a blueprint packaged
as `bp`, and then the two records name the same artifact differently.

Both are right for their own job. The packaged name answers "what is this
blueprint" and belongs in provenance. The called name answers "what did
this stack ask for" and belongs in a file a person edits and reconciles
against their own declaration. Forcing either to adopt the other makes one
of those answers wrong, so neither does.

Anything joining the two therefore cannot use a name. It cannot use the
content hash either, tempting as that is: two versions of a blueprint are
different bytes by construction, so the hash stops matching exactly when a
version changes, which is the case a comparison usually exists to find.

What survives both is the identity of the source with its version
stripped, which is the same derivation the lock already uses for its key.
`oci://host/repo:v1` and `oci://host/repo:v2` produce one value. See
[Restore](/concepts/restore), where the reconciliation that needs this
lives.

### It makes the cache correct, not just tidy

The dependency cache was keyed on the declaration string, for a reason
its own code explained: there was no trustworthy content hash to key on
before pulling. A cache hit re-verified the directory against its own
manifest, which establishes self-consistency and never asks the registry
anything.

So a repointed tag left every machine that had already pulled on the old
content indefinitely, while a machine pulling for the first time got the
new content. Both verified successfully. Nothing anywhere noticed.

The distinction matters more than it looks, because the obvious reading
is wrong. A cache keyed on a mutable name sounds like it would clobber:
the new content arrives, overwrites the old, and something breaks
loudly. It did not do that. It never re-fetched at all, so the first
version pulled on a given machine stayed there permanently, and the
population diverged by who happened to pull when.

A clobber is loud and local, and the next run finds it. A permanent
silent stale serve is neither, and it produces machines that disagree
with each other while every one of them reports success. Only the first
is what "cache collision" suggests, which is exactly why it is worth
stating.

A lock entry is exactly the trustworthy pre-known hash that was missing.
Storage is now content-addressed and nothing else: one directory per
content hash, with tags resolving through a stack's lock the way a
container runtime keeps digests as storage and tags as pointers. Two
stacks pinning the same content through different tags stop being two
cache entries.

The consequence is deliberate rather than an oversight: a stack with no
lock entry has nothing to look content up by, so it fetches every time.
Caching a mutable pointer locally is the unsoundness being removed, not
a convenience to preserve, and the cost is one command to adopt the
lock.

That layout would have been a regression in legibility on its own, since
a directory of bare hashes says nothing about what any of it is. So an
origin index is written at pull time, which is the only moment both the
source and the resulting hash are in hand: a blueprint's own manifest
records a hash and no origin, and a stack's lock knows only about that
stack. `ubx blueprint list` reads it. The index and the layout arrived
together on purpose, because an index nothing reads is a file that
rots.

### Making it importable, without owning files ubx does not own

A declaration is only useful if the program can then import what it
names. That is the part a language module resolver decides, and each of
the three decides it differently, so this is where one mechanism has to
become three adapters.

The constraint that shaped all of them: **ubx writes only into files it
owns.** Reaching into an author's `go.mod`, or creating a `node_modules`
directory, would put ubx in a tug of war with tooling that rewrites
those files on its own schedule. A `go mod tidy` or an `npm install`
would quietly undo it, and the failure would arrive later, somewhere
else, looking like something unrelated.

That constraint turned out to cost nothing, which was not obvious in
advance and was worth checking before designing around it.

TypeScript already had the mechanism. The evaluator generates an import
map for every run, merges the project's own into it, writes it to a
temporary file and names it on the command line. A blueprint is one more
entry in a file that exists for a few hundred milliseconds. Nothing in
the project is read for write or created.

Go looked like the hard one, and stopped being hard once the evaluator
learned to synthesize a workspace for an unrelated reason: it had to
carry a program's own workspace through the throwaway module copy it
builds from. A blueprint is one more member of that workspace. A
workspace member is importable without anything requiring it, which is
the property that matters here, because a stack that declares a
blueprint in config has no requirement for it anywhere and should not
need one.

Python needs neither, since an interpreter path is already ubx's to set.

### One stamping pass, not two

Attributing a resource to the blueprint that produced it used to work by
walking the program's own module graph after evaluation. That is sound
when the only way to reach a blueprint is to import it from somewhere on
disk, and it stops being sound the moment a blueprint can be declared: a
declared one is resolved before the program runs and never appears in
the program's own graph at all.

The symptom was precise and worth remembering, because it is the shape
this class of bug takes. Evaluation succeeded, the blueprint was
fetched, verified and imported, the program ran, and then attribution
refused a name it had itself just resolved. Two mechanisms that were
supposed to agree about what a program depends on, disagreeing, with
only one of them holding the whole answer.

Both halves now come from the same place: the evaluation returns what it
resolved, declared and discovered together, and attribution reads that
rather than asking again.

## A blueprint's own dependencies

Making a blueprint importable is one problem. What the blueprint itself
imports is another, and it was not solved by the same mechanism.

A blueprint's declaration travels: its `deno.json` or `package.json` is
an ordinary file in the blueprint directory, so it is in the content
store and covered by the content hash exactly as the source is. Nothing
read it. ubx merged the *consumer's* declaration into the import map and
never the blueprint's, so a blueprint that imported anything by a bare
specifier could not run at all.

Reading it is the fix, and it raises a real question rather than a
mechanical one: a declaration can name a registry, and honouring that
means reaching the network while evaluating.

### The boundary is the pin, not the specifier

The answer is not "registry dependencies are refused" and not "registry
dependencies are allowed". It is that a **pinned** dependency graph may
be fetched and an **unpinned** one may not.

Specifier kind was the obvious test and it is the wrong one. It is a
proxy for pinnedness, and a bad proxy: a registry specifier accompanied
by a lock is pinned, the same specifier without one is not, and nothing
about the specifier distinguishes them. A lock is the only evidence of
the property that actually matters, so the lock is what the boundary
tests.

That makes the lock load-bearing, which raises the question of where it
comes from.

### The lock is generated at packaging time

The original design assumed a `deno.lock` would simply be present,
because a blueprint author installing dependencies produces one. That
assumption was wrong, and the way it was wrong is worth recording: it was
verified by running `deno install` on a test fixture, which is not what
an author does. `npm install` writes `package-lock.json` and no
`deno.lock`, and deno does not read npm's lockfile at all.

So requiring a lock would have refused every npm-authored blueprint, and
the remedy would have been running a Deno command inside something the
author thinks of as an npm package.

`ubx blueprint package` generates it instead, before the manifest is
built, so the hash covers it. Packaging is the one moment ubx holds the
whole blueprint, and it already derives the blueprint's schema at exactly
this point for exactly this reason. Both artifacts are re-derived on
every package rather than reused: one that could be stale defeats the
reason it is derived.

<Warning>
**This gave packaging a network dependency it did not have.** `ubx
blueprint package` now reaches the network, and needs `deno` on `PATH`,
for a TypeScript blueprint that declares npm dependencies. That is a
change in what the command is, not an implementation detail. It is scoped
to blueprints that declare such dependencies; every other blueprint,
including every one ubx itself generates, packages offline as before.
</Warning>

### Fetching is a pass of its own

deno accepts one `--lock` per invocation, so the blueprint's lock cannot
be handed to the consumer's evaluation. Both ways of trying fail, and
they fail differently:

- With `--frozen`, deno refuses, because `--frozen` validates the lock's
  own workspace section against the workspace being evaluated, and the
  blueprint's lock describes the blueprint's workspace.
- Without `--frozen`, deno **rewrites the lock file**. That file lives in
  content-addressed storage, so writing to it would mutate the content
  that the hash identifies.

So fetch-and-verify is a separate invocation, against the blueprint's own
workspace, and evaluation is a second one. This is the same split ubx
already uses one level up, where pulling and verifying a blueprint is a
distinct step from using it.

What that pass buys is two things worth separating, and the first was
learned the hard way.

### Where the dependencies have to physically be

The first version of this fetched into deno's global cache and stopped
there, on the reasoning that a cache hit is a cache hit. That works only
while the consumer's own project has no `package.json`. One anywhere deno
discovers from the module graph root puts the **whole graph** into
node_modules resolution, and in that mode the global cache is not
consulted at all:

```
Could not find "@ubx/sdk-aws" in a node_modules folder.
```

A consumer with a `package.json` is the documented setup, so this failed
for the ordinary case and passed for the test fixture, which had none.
The symptom is also indistinguishable from the pass not running, which is
how it was first reported.

deno resolves a bare npm specifier by walking up from the importing file,
so the dependencies have to be in a `node_modules` **adjacent to the
blueprint itself**. That location is the whole design question, because
the obvious place is the wrong one.

Inside the content store would work. `node_modules` is excluded from the
manifest, so the content hash is unaffected and verification still
passes. It is still wrong: the store is immutable by design and much of
what is built on top assumes it, and two concurrent plans would both run
`deno install` inside one store directory with nothing arbitrating them.
Trading a load-bearing invariant for a directory saved is a bad trade.

So the dependencies are materialised **beside** the store, at
`deps/sha256/<hex>`: one symlink per store entry plus a real
`node_modules`, built in staging and renamed into place, with evaluation
rooted there. The store keeps its one job, which is to hold verified
content and nothing else.

One detail that had to be checked rather than assumed: deno does **not**
resolve those symlinks and walk up from the store instead. Had it done
so, the arrangement would have looked right and quietly done nothing.

Reuse is gated on the mirror still **resolving**, not merely existing. A
blueprint declared from a local path is staged into a temp directory, so
a mirror of one can go stale while its content hash stays identical, and
a presence check would hand back a directory whose every file had
vanished.

### Exactly one runtime instance

Making a blueprint's dependencies resolvable created a new way to get
one of them wrong, and it was the most important one.

An npm-authored blueprint **must** declare `@ubx/sdk` in its
`package.json`: it cannot install or type-check without it. ubx read that
declaration like any other and turned it into an `npm:` entry in the
blueprint's own scope. A scope is consulted before the top level, so ubx
itself displaced the embedded runtime with the published package, and the
blueprint ran against a second copy:

```
Error: resource() called outside of an active stack() evaluation.
  at requireCollector (.../node_modules/.deno/@ubx+sdk@1.0.3/dist/index.js)
  at dupbp (.../deps/sha256/.../blueprint.ts)
  at Object.evaluate (.../ubx-tseval-*/runtime/src/index.ts)
```

Both runtimes are in that one trace. The collector `resource()` writes
into is module state, so a second instance is a second collector, and the
blueprint's has no active stack behind it.

Worth being exact about the cause, because the obvious reading is wrong.
Nothing shadowed the import map. An import map entry does beat
node_modules resolution; ours simply pointed at npm.

So the runtime is pinned to the embedded copy inside every blueprint's
own scope, and the declaration is skipped where it is read. Either alone
is sufficient, which is recorded in the code so that a test passing does
not get mistaken for both halves working.

### Why the override cannot be relaxed

It would be reasonable to ask whether a blueprint should be allowed the
runtime version it pinned. It cannot, and not for reasons of preference.

The published `@ubx/sdk` does not export `__setBlueprintRoots`, the
channel the generated runner uses to tell the runtime which directories
belong to which blueprint. A blueprint running on its own copy could not
take part in provenance at all, even with the collector problem solved
separately. The embedded runtime is the only one that can do the job.

There is precedent rather than a new rule: a consumer's own `@ubx/sdk` is
already overridden the same way, so that evaluation works offline and
against the runtime this binary shipped with.

### What that costs, and why it is acceptable today

A blueprint published once may be evaluated by any later `ubx`. The
author chose neither the binary nor the runtime it carries.

That is safe today and was checked rather than assumed: the embedded
runtime and the published package export the same 24 names, and the
embedded one is a strict superset. When the surfaces do diverge, a
blueprint wanting an export an older runtime lacks fails loudly, at
module evaluation, naming the missing symbol. Loud is what makes this
tolerable; it is not silently wrong.

It is still a gap, and it has two named pieces. The embedded runtime
declares a version unrelated to the published one, which is harmless only
while nothing compares them. And a blueprint records nothing about what
it was built against, which is what would let a mismatch be refused when
it is pulled rather than discovered when it runs.

### Verification, which nothing else provides

The second thing the pass buys is that the bytes are checked against the
blueprint's own lock before anything runs. Without it, evaluation would
take whatever the registry served and the blueprint's lock would be
decorative. So the test that matters is the refusal of tampered bytes,
not the success of honest ones.

### The alternative, and why it was measured rather than argued

Passing `--node-modules-dir=none` to the evaluator would also have fixed
the resolution failure, by opting the whole graph out of node_modules
mode instead of giving the blueprint its own.

It was rejected on measurements, not taste. A consumer holding a
populated `node_modules` re-downloads those packages, and a consumer with
no network cannot plan at all. Both were reproduced. The point of the
boundary is that a blueprint cannot pull in unpinned code; it is not
worth paying for that by taking away the consumer's own resolution.

### JSR is blocked, by a flag that should stay

An npm dependency works. A JSR one does not, and no lock changes that.

The evaluator runs deno with `--no-remote`, which is the flag that
actually closes the dynamic `import("https://...")` gap. It does not
block npm. It does block JSR, because resolving a JSR package fetches
`https://jsr.io/<pkg>/meta.json`, and that is a remote specifier. This
holds against a fully warm cache, so it is a resolution-time rule rather
than a caching artifact.

This matters more than a missing feature usually would: the published
Ubiquex TypeScript SDK is distributed on JSR. So "registry dependencies
are supported" is false for exactly the registry an author is most likely
to reach for, and lifting it means narrowing a security flag rather than
extending a resolver.

### What is pinned, and what is not

The blueprint's half becomes pinned. Evaluation still reaches the network
for the consumer's own dependencies, which remain the consumer's business
and are governed by the consumer's own lock exactly as before. deno
resolves a workspace's npm dependencies eagerly regardless of what the
entry file imports, so this cannot be narrowed by touching fewer things.

The boundary is not that evaluation becomes network-free. It is that a
blueprint someone else wrote cannot introduce code that nobody pinned.

One related correction landed with it: evaluation no longer rewrites the
author's `deno.lock`. deno updates a project's lock as a side effect of
running, so reading a stack left a diff in a file the author owns. ubx
now points deno at a copy, which is the same shape as the Go evaluator
carrying a program's `go.mod` into a throwaway build directory rather
than editing it.

### The Go half of the same boundary

Everything above is the TypeScript side. Go reaches the same place by a
different route, and the differences are the interesting part.

The failure was identical in shape. A declared Go blueprint importing
anything outside the standard library ran on a machine that already
happened to have the module cached, and nowhere else:

```
github.com/google/uuid@v1.6.0: module lookup disabled by GOPROXY=off
```

`GOPROXY=off` is deliberate, the same posture `--no-remote` gives the
TypeScript evaluator: evaluation does not fetch code. So the bytes have
to be present before evaluation starts, which means a prefetch, and a
prefetch is only safe against something pinned.

#### Go is refused rather than pinned for you

This is where the two languages part, and the reason is about ownership
rather than tooling.

Packaging a TypeScript blueprint generates the lock it needs, because
`deno install` writes a lock file *beside* the source and leaves the
source alone. Go's equivalent does not. `go mod tidy` rewrites the
author's `go.mod` and changes what their module requires, observed
bumping a fixture's own `go` directive unasked.

Packaging is not the place to change what someone's module requires, and
an author should see that diff rather than discover it applied. So an
unpinned Go blueprint is refused, naming the command and the file that
fixes it. The author hits that wall once per blueprint and keeps control
of their own module.

The boundary itself is unchanged between the two languages: a blueprint
cannot introduce code nobody pinned. Only who writes the pin differs.

#### And no mirror, because Go resolves differently

The TypeScript side needs a directory of symlinks beside the content
store, because node_modules resolution walks *up* from the importing
file and a blueprint sitting in the content store has nothing above it.

Go resolves from a module cache instead, so where the blueprint sits does
not matter and a populated cache is enough.

That cache is the consumer's own, not one `ubx` owns, and it was settled
by measurement rather than preference. Go has exactly **one** module
cache per build. Pointing `GOMODCACHE` at an ubx-owned cache holding only
the blueprint's dependencies breaks the consumer's own resolution, which
was reproduced rather than predicted. An isolated cache sounds tidier
right up until it takes the consumer's dependencies away from them, which
is the same trade the `--node-modules-dir=none` alternative lost on
above.

## Sensitive parameters

A parameter can declare that its argument carries a credential, written as
a trailing clause: `api_token: string, required, sensitive`.

It governs **recording and nothing else**. A blueprint receives a
sensitive argument exactly as it receives any other, nothing traces the
value through it, and whether a resource attribute is protected is decided
by the provider's own schema rather than by this. Two mechanisms, two
authorities, and a reader who assumes otherwise is protected less than
they think.

The narrow scope is deliberate rather than unfinished. Constraining use
would mean tracing a value through a blueprint written in any of three
languages, which nothing here can do, and a flag that half-constrained use
would be worse than one that plainly does not.

### A sensitive parameter cannot have a default

Refused at packaging time. An `Ubxfile` ships **inside** the packaged
blueprint, so a default written there is distributed: a sensitive default
hands the credential to everyone who pulls the blueprint, and it leaks
without anyone running anything. That is strictly worse than the case the
flag exists to prevent, so it is a refusal rather than a warning.

### Three markers, one per language

A code blueprint marks a parameter with its own language's metadata
mechanism: a Go struct tag, Python's `Annotated`, a TypeScript JSDoc tag.

Three idioms rather than one spelling, which is the correct outcome rather
than a compromise. The alternative, a single `Sensitive<T>` wrapper spelled
three ways, would read more uniformly and change the type the blueprint
receives, forcing every author to unwrap a value to satisfy a flag that
governs nothing about how they use it. A recording concern should not be
visible in code that has no business knowing about it.

The same blueprint marked in any language produces the same schema, and a
test asserts that across all three. If a language ever cannot express it,
the rule is to stop carrying sensitivity in the schema entirely rather
than ship it for two out of three: a blueprint that silently stops
protecting a credential when ported is a trap dressed as a feature.

### It changes the packaged schema, and older versions refuse it

A blueprint with sensitive parameters is packaged at schema version 2, and
an older `ubx` refuses it rather than reading it.

That refusal is the mechanism rather than its cost. A binary that cannot
tell which parameters carry credentials has no safe way to record what a
call was made with, so refusing is the only honest response. Relaxing that
gate into a warning would turn a refusal into a leak.

## List parameters and iteration

A blueprint that needs to create a variable number of resources, one
subnet per availability zone the caller passes in, uses a
`list(string)`/`list(number)` param and a `for_each` field, set directly
on the one resource that iterates in the author's own pre-resolved
`resources:` document -- a real, structured field, never inferred from
prose. No new runtime construct exists in any of the three SDKs for
this either: Go, TypeScript, and Python already have a `for` loop, so
compiling a `for_each` resource down to one is an ordinary codegen step,
real bare `{param}`/`{param_index}` tokens resolved per language. At
most one iterating resource per blueprint, never the target of a
sibling's own reference, never combined with `outputs:`, each a hard
build-time refusal, not a silent limitation.

## Overriding a blueprint's internals

`override(address, {field: value})`, called from the SDK, patches a
resolved attribute the blueprint's own author didn't expose as a
parameter, applied after a call expands, before the resolver runs. Real, named
scope boundary: this only ever targets a resource created within the
SAME resolving document, it does not retroactively patch an address
that already exists in the ledger. Forward-looking insurance for a
future re-call, never a live ledger patch. Policy-bypass protection for
this mechanism is documented but not enforced, the policy engine that
would enforce it (UBI-118) doesn't exist yet, so every override
currently succeeds regardless of what it targets.

## Composing with hand-written resources

A blueprint call's own output feeds a hand-written resource in the
same stack cleanly, no special case in the resolver at all. A
hand-written resource's own value cannot feed back into a blueprint
call, in either calling direction, structurally, not as a missing
feature. See [Blueprint Composition](/concepts/blueprint-composition)
for the full account of why, and how provenance is stamped regardless
of which of the two real calling paths a caller actually used.

The identical restriction applies to a SIBLING blueprint call's own
output, not only a hand-written resource's -- a stack whose only
content is blueprint calls, no hand-written resource at all, can author
those calls in plain HCL instead of the SDK. See
[HCL Blueprint Calling](/concepts/hcl-blueprint-calling) for the
grammar and for the same reference-direction wall found again, this
time as a real, tested finding against a ticket's own worked example.

## What this isn't

Nesting one blueprint inside another (`uses:`) is real, separately
tracked, separately designed work, not something a blueprint call does
today. There's no hosted registry service either: every real
distribution mechanism talks to infrastructure that already exists
(GHCR for OCI, git directly) rather than a bespoke service `ubx` would
have to run itself, and none of the four real distribution mechanisms
is a discovery mechanism, a caller always already knows the ref.

Full detail, including the calling convention
and the trust model behind each distribution mechanism:
[`docs/blueprint.md`](https://github.com/Ubiquex/ubiquex/blob/main/docs/blueprint.md)
in `ubiquex`. An AI assistant can help with the Author and Build stages
directly, through five MCP tools that return content rather than
writing to a repository -- see [MCP Tools](/concepts/mcp-tools) for the
contract and why `push_blueprint` (the Distribute stage) is deliberately
not one of them.
